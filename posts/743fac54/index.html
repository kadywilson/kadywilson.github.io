本地智能桌宠第三期：让桌宠“读到”我的日记

第三期其实不是单纯给桌宠加一个新按钮，而是把两个本地项目接起来了。

一个是之前一直在写的 smart-desktop-pet，也就是本地智能桌宠；另一个是我之前做的 diary_ai，一个可以读取我的日记、生成摘要和反馈的小项目。

一开始我想做的是：让桌宠用本地 TTS 把日记反馈读出来。

最后实际落地的是：不朗读，不上传，只把一段“今日小纸条”写进桌宠的聊天记忆里。

这期主要更新了什么

第三期主要完成了三件事：

  1. 试了一轮 VoxCPM 本地 TTS，然后决定放弃。
  2. 单独整理并增强了 diary_ai 项目，包括收藏反馈和发送给桌宠。
  3. 桌宠新增 Diary Feedback 菜单，可以读取日记小纸条并写入当前聊天记忆。

这个区别还挺重要的。

一次本地 TTS 尝试：VoxCPM

最开始我确实很认真地研究了一下 VoxCPM。

因为我的想法是：如果日记反馈比较私密，那就不适合发给火山引擎 TTS。日常聊天气泡可以用火山引擎朗读，毕竟内容比较短，也不太敏感；但是日记反馈不一样，它可能涉及当天发生的事、情绪、压力、计划，甚至一些不想被第三方服务处理的内容。

所以我想：那就本地跑 TTS 吧。

VoxCPM 的优点很明显：

  • 可以本地生成语音。
  • 可以用提示词定制音色。
  • 音色好听，语气比豆包自然。
  • 不需要把文本发送给外部 TTS 服务。
  • 理论上很适合读比较私密的内容。

我还根据桌宠的人设生成了一批男声音色提示词，并且生成了几条样音。最后挑出了一个比较满意的声音

但是实际接入时问题就来了。

生成速度太慢

我的电脑是笔记本，虽然有 NVIDIA GPU，也能跑起来，但是16G实在是太小了呃呃呃，VoxCPM 的生成速度明显不适合日常交互。

尤其是日记反馈本身又很长，哪怕分段朗读，也会变成一个很重的任务。

环境也开始变复杂

接入 VoxCPM 以后，环境里出现了比较典型的本地模型依赖问题。

比如 NumPy 版本升级导致 PySide6 / shiboken6 出现 ABI 警告：

桌宠对我来说首先应该是轻量、随时可用、不要折腾。

所以最后决定：

  • 日常语音继续用火山引擎。
  • 日记相关内容不发给火山引擎。
  • VoxCPM 暂时完全移除。
  • 不在桌宠环境里保留 torch / voxcpm 这一套依赖。

这个决定做完之后，项目一下子清爽了很多。

单独介绍一下 diary_ai

diary_ai 是另一个本地项目，目录在：

它的 conda 环境叫：

这个项目的核心作用是：读取我某一天的日记，然后让 AI 生成摘要和反馈。

它不是桌宠的一部分，而是一个单独的本地 Web 小工具。

它现在能做什么

目前 diary_ai 主要有这些功能：

  • 选择某一天的日记。
  • 读取日记内容。
  • 生成当天摘要。
  • 根据历史摘要和日记生成 AI 反馈。
  • 可以重复 roll 反馈。
  • 可以更新当前摘要。
  • 可以收藏满意的反馈。
  • 可以选择是否把收藏反馈写回日记。
  • 每天定时邮件发送日记反馈。
  • 可以把当天摘要导出给桌宠。

这里最重要的是：摘要和反馈是两个不同层级的东西。

摘要更像是“今天发生了什么”的压缩版本，并且可以写入json给AI提供历史日记上下文；反馈则是 AI 对这一天的回应，可能更长、更主观，也更像一封给自己的回信。

摘要缓存

diary_ai 里有一个摘要缓存目录：

这个目录本来是记录历史摘要给AI日记伴侣提供上下文的，正好可以重复利用把摘要发送给桌宠。

因为我不希望每次点击“发送给桌宠”都重新调用 AI。很多时候我已经生成过摘要了，只是想把这一天的背景发给桌宠，让他在之后聊天时知道。

所以现在的逻辑是：

  • 如果这一天已经有摘要，可以直接发送给桌宠。
  • 如果这一天没有摘要，就提醒我先读取日记或更新摘要。
  • “发送给桌宠”本身不调用 AI。
  • 它只使用已有摘要缓存。

这个改动非常符合实际使用习惯。

因为我可能已经生成过摘要，也可能已经 roll 过好几版反馈了。发送给桌宠应该是一个独立动作，而不是强迫我重新跑一遍 AI。

diary_ai 的隐私边界

这个项目里也有 .env，里面会有真实 API key 和邮件配置。

规则很简单：

  • 不读 .env
  • 不打印 .env
  • 不把真实 key 发给 AI
  • 不随便跑邮件脚本
  • 不把原始日记导出给桌宠
  • 不把完整 AI 反馈导出给桌宠

这次联动里，桌宠拿到的不是原始日记，也不是完整反馈，而是一段由摘要生成的“桌宠上下文”。

为什么不是直接把日记全文发给桌宠

中间我也想过：既然想让桌宠知道我今天发生了什么，为什么不直接把日记发给他？

后来想想，不太合适。

原因有几个。

1. 原始日记太长

桌宠的 Chat memory 是轻量 JSONL，不适合塞一大段原始日记。

如果直接把全文写进去，之后每次 Chat 都可能把大量无关内容注入 prompt，既浪费 token，也会让对话变得笨重。

2. 桌宠不需要知道所有细节

桌宠不是日记分析器。

它不需要知道每一句原文，也不需要复述我的日记。它只需要知道一个温柔的背景：

所以最后选择了中间方案：不发原文，使用摘要生成一段桌宠上下文。

为什么不显示长气泡

一开始我还想过：点击 Diary Feedback 后，要不要让桌宠把日记反馈一段一段显示在气泡里？

后来放弃了。

原因很简单：日记反馈太长了。

桌宠气泡适合短句，不适合大段阅读。长文本塞进气泡会产生几个问题：

  • 气泡巨大。
  • 文字密度太高。
  • UI 很容易挤压或超出屏幕。
  • 桌宠从“陪伴”变成“弹窗阅读器”。

所以最后只显示简短确认：

真正的反馈阅读还是在 diary_ai 网页里完成，桌宠只负责“知道”。

这次的关键取舍

这一期最核心的不是技术实现，而是几次取舍。

1. 日常语音和私密内容分开

日常桌宠气泡可以用火山引擎 TTS。

但是日记内容不发给 TTS。

这条边界很清楚：

2. 本地模型不是越多越好

VoxCPM 能跑，但不代表适合这个项目。

桌宠是一个长期挂在桌面的小工具，它更需要稳定、轻量、启动快、少出错。

如果一个功能会让环境变复杂、启动变慢、依赖变重，那它就算技术上很酷，也不一定值得留下。

3. 不把所有东西都塞进桌宠

diary_ai 和桌宠是两个项目。

diary_ai 负责读日记、生成摘要、生成反馈、收藏反馈。

桌宠负责陪伴、短对话、提醒、天气、接收一段轻量上下文。

它们之间只通过一个 latest.json 交接。

这个边界让我很安心。

总结

第三期表面上是新增了 Diary Feedback，实际上是把桌宠从“能聊天的小工具”往“更懂当前生活上下文的本地伙伴”推进了一点。

但我不想让它变成一个什么都读、什么都存、什么都上传的大系统。

所以这期最后形成了几个原则：

  • 日记原文不进桌宠。
  • 完整 AI 反馈不进桌宠。
  • 日记内容不发给 TTS。
  • 桌宠只接收摘要派生的“今日小纸条”。
  • 小纸条写进 active chat memory，并随 archive 自然归档。
  • VoxCPM 暂时退出，保持桌宠环境轻量稳定。
